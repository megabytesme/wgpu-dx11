# Direct3D 11 native API gaps

This source review uses wgpu `aa7b65c43ef008d0a92d20fcdf9f10fa0883f157` and covers FL9_1 through FL11_1. A capability may be present on a physical driver, implemented in the fork, expressible by wgpu, and verified on the target device. Each is a separate claim. The current normal adapter uses the FL9_1 projection even on higher native devices. The table below records gaps that prevent literal native tier certification, including features with a portable approximation. [Adapter projection](../wgpu-hal/src/dx11/adapter.rs#L19) · [Projection limits](../wgpu-hal/src/dx11/capabilities.rs#L857) · [Microsoft feature levels](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-devices-downlevel-intro)

## Classification

| Classification | Application to a certification row |
| --- | --- |
| **Native API blocker** | A mandatory feature lacks a reachable interface or exact semantics in the fork. Keep it open until an approved interface executes it and passes its native, backend and applicable public cases. |
| **Implementation blocker** | The API expresses the operation, but projection, validation, resource creation, compilation, recording or execution is missing. Add the implementation and verify the existing entry point. |
| **Conditional** | The operation is required when a specified format, runtime or reported option applies. Save the triggering evidence with the row. Exercise both the triggered case and the absent or unsupported path. |
| **Optional** | A query can report support, but the tier has no unconditional obligation. Test each advertised option end to end. An unavailable interface/HRESULT, an available query returning false, and a supported operation are distinct outcomes. |
| **Native prohibition** | Record the documented restriction and verify its negative boundary. A portable alternative may be valid if it preserves its advertised semantics. |

D3D9 driver-side prerequisites for 10Level9 remain separate evidence from operations callable on a D3D11 device. D3D11.1 runtime availability and the selected native tier have separate fields. Where Microsoft’s driver-level and API-level tables differ, record both and verify the externally callable behavior at the exact tier. ## Geometry and stream output

1. FL10_0 requires the native geometry and stream-output stages. The closure path needs HLSL profile selection, actual D3D11 geometry shader creation and binding, topology compatibility for points/lines/triangles and adjacency, output primitive emission, optional rasterized stream selection when available, stream-output declaration, buffer binds, and query/counter behavior. Test every profile where a stage is claimed. FL11_0 adds the SM5 GS instance and stream variants. [Native geometry stage](https://learn.microsoft.com/en-us/windows/win32/direct3d11/geometry-shader-stage) · [Native stream output](https://learn.microsoft.com/en-us/windows/win32/direct3d11/d3d10-graphics-programming-guide-output-stream-stage)
2. A baseline native fixture should use data with unique primitive, vertex and stream ids, write distinct fields to stream-output buffers and read them back. Add invalid topology, component count and stride cases. Use late bound buffers and switches between pipelines with and without GS/SO to test reset. For the SM5 variant test 32 instances, four streams and independent output vertex/scalar limits. After generating capture data, execute `DrawAuto` on the same output buffer as IA input and verify its coordinate/color output. A compute shader that writes a buffer and an ordinary indirect draw are useful portable alternatives, with distinct native test identities. [Functional specification, §§8.9, 13–14](https://microsoft.github.io/DirectX-Specs/d3d/archive/D3D11_3_FunctionalSpec.htm)
3. The existing HAL render descriptor, encoder playback and Naga pipeline selection require additional reachable data. A DX11-only route may accept audited FXC DXBC or typed source/entry descriptions and map the stage into HAL resources. An approved Rust extension would need shader stage representation, pipeline/primitive descriptors, stage visibility and interface validation in Naga and Core, plus HAL playback and independent public tests. Bind counts, resource hazards and pipeline changes must be verified on the actual stream-output path. [Public render descriptor](../wgpu/src/api/render_pipeline.rs#L199) · [Public primitive topology](../wgpu-types/src/render.rs#L371) · [Naga shader stage](../naga-types/src/lib.rs#L117) · [Current FXC selection](../wgpu-hal/src/dx11/hal_shader.rs#L11311)

## Hull and domain tessellation

1. FL11_0 adds `hs_5_0` and `ds_5_0`. A reachable backend implementation needs HS/DS shader objects and paired pipeline binding, patch topology and count, compatible VS/HS/DS linkage, domain, partitioning mode, control-point and patch-constant declarations, resource bindings, and deterministic cleanup as the pipeline switches to ordinary primitives. Include tessellation plus GS/SO and separate shader profiles. FL11_1 paths additionally need shared OM UAV access from both shader stages. [Tessellation stages](https://learn.microsoft.com/en-us/windows/win32/direct3d11/direct3d-11-advanced-stages-tessellation) · [All-stage UAV access](https://learn.microsoft.com/en-us/windows/win32/direct3d11/direct3d-11-1-features)
2. Use known patch positions and factors on tri, quad and isoline domains, then measure deterministic pixels, counters or captured evaluated vertices. Exercise 1 and 32 points, invalid 33, mismatched domains/stage declarations, integer and fractional partitions, factors at legal extremes and documented clamp/cull behavior including zero, and shader/resource changes across consecutive draws. A native-only HLSL pass supplies driver evidence. The identical requirement still needs a caller-reachable backend operation and an observable result in the integrated candidate. [Per-stage tessellation constraints](https://microsoft.github.io/DirectX-Specs/d3d/archive/D3D11_3_FunctionalSpec.htm)

## Implementable portable paths

The existing API describes multiple render targets, compatible independent blending, depth/stencil and indexed draw modes, compute, storage buffers/textures, ordinary indirect draw/dispatch, public occlusion and timestamps. These need gated implementation and test results even if a separate native extension is also proposed. For example, the HAL currently rejects compute pipeline creation, lacks indirect recording and leaves timestamp features disabled while submission-wide disjoint tracking is missing. At FL11_0, graphics UAVs share the eight OM slots with RTVs. FL11_1 separates 64 CS slots from 64 OM registers shared across graphics stages. For both tiers coordinate per-stage visibility, physical register assignment, an aggregate RTV plus storage budget, distinct typed-load/support flags, and explicit unbinds across SRV/UAV/RTV/DSV conflicts. Promoting a feature bit before those checks can expose unsupported valid workloads. [Compute creation](../wgpu-hal/src/dx11/hal_device.rs#L1117) · [Indirect recording](../wgpu-hal/src/dx11/hal_encoder.rs#L2508) · [Timestamp exposure test](../wgpu-hal/src/dx11/capabilities.rs#L2673) · [UAV register semantics](https://microsoft.github.io/DirectX-Specs/d3d/archive/D3D11_3_FunctionalSpec.htm)

For options like FL10_x DirectCompute 4.x, require the actual optional feature query, the restricted shader and descriptor limits, and deterministic results. Compute version, broad public compute/storage guarantees and optional hardware format support may differ. FL11_1’s required `D3D11_OPTIONS` members must be true, with SAD4 and extended doubles optional. Basic double precision has a separate query. Newer runtime options such as tiled resources or additional typed UAV loads still depend on interface/version and driver facts, and keep separate optional tests. [DirectCompute rules](https://learn.microsoft.com/en-us/windows/win32/direct3d11/direct3d-11-advanced-stages-compute-shader) · [11.1 options](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ns-d3d11-d3d11_feature_data_d3d11_options) · [Typed UAV loads](https://learn.microsoft.com/en-us/windows/win32/direct3d11/typed-unordered-access-view-loads)

## Design decision for a reachable interface

| Design | Suitable scope | Obligations |
| --- | --- | --- |
| Existing portable operation | Native implementation can preserve the public semantics and its whole capability contract. | Keep normal device/pipeline/encoder entry points and validation. Verify projection, implementation and public outcomes. |
| DX11-specific Rust or HAL extension | Exact D3D11 objects, feature queries, HLSL stages, DXGI views, state and context operations. | Define an explicit opt-in descriptor/command path with typed operations and backend capability checks. Preserve device/resource ownership, context locking, submission order, aliasing, initialization, lifetime, and device-loss propagation. Make scope and unsafe preconditions explicit. Validate difficult interop with actual downstream consumers and affected fallback paths. |
| New cross-backend Rust feature | Semantics are portable across supported backends and the broad representation is agreed with the API owners. | Define feature and limits, Core validation, HAL contracts and Naga language/IR work as needed. Keep feature-default behavior, run targeted cross-backend and affected CTS/test coverage, and retain any distinct native-only differences as open rows. A wgpu Rust extension does not automatically extend the WebGPU or WGSL standard. |
| Standalone native fixture or raw interop | Native driver evidence, owned prototype and conformance oracle. | Use exact physical device and record native calls/results. The generic unsafe `as_hal` and import entry points do not currently provide DX11's native GS/HS/DS/stream-output pipeline or typed operation path. Raw state mutation around wgpu can violate its resource tracking. Define an approved explicit ownership and synchronization boundary before offering interop as an implementation. |

The pinned fork's raw device and immediate-context methods are crate-private, and the immediate context is accessed through a mutex guard. The current external HAL texture import requires the same internal device and matching descriptor and state. Any proposed interface must preserve those invariants or define a reviewed transfer boundary with equivalent guarantees. [Native device access](../wgpu-hal/src/dx11/device.rs#L367) · [wgpu HAL import safety](../wgpu/src/api/device.rs#L331) · [Encoder HAL access](../wgpu/src/api/command_encoder.rs#L277)

Record the approved route, exact reachable constructor and operation, negative validation evidence, native readback, matching fork readback, relevant wgpu checks and the signed or desktop physical record under the requirement’s durable ID. Attach the immutable candidate SHA, device and driver/runtime identity, source and package provenance where applicable, and independent review. Keep each mandatory gap **BLOCKED** while an API decision, implementation, runtime or physical test is outstanding.
