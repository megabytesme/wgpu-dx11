# FL10_0 and FL10_1 research and acceptance packet

Baseline: wgpu `aa7b65c43ef008d0a92d20fcdf9f10fa0883f157`. Both tiers are **INCOMPLETE**. Findings here come from source and specifications. Every proposed physical test below is unrun in this packet.

## Format requirements and important caveats

Track each pair of DXGI format and usage. Format support for a resource says little about whether the same typed view is renderable, blendable, filterable, shareable, or usable as a different API view.

- **FL10_0 formats.** Native BC4/BC5 UNORM and SNORM join BC1–BC3. Full wgpu `TEXTURE_COMPRESSION_BC` also promises BC6H/BC7, which FL10_x does not guarantee. Add a narrower public feature or report the representability gap for the BC4/5 subset. Confirm BC resource shape/mips, signed endpoint and block edge behavior, upload/readback and lookup. FL10_0 also adds integer texture types, signed-normalized RT uses, D32F and D32F/S8 DSVs, shader casts from compatible typeless resources, mip autogeneration and formats recognized solely for native typed buffers. Probe a positive operation and a mismatched type, usage or typed view for each guarantee. Native DSV formats and SRV interpretations need separate rows. Wgpu's float32 blend/filter features apply to a family of formats and must be compared with the exact family guarantees in `wgpu-types/src/features.rs:1770`.
- **FL10_1 format deltas.** A status comparison across the two Microsoft Learn tables found 124 transitions into required cells (109 format sections per tier). They comprise 38 for 4× render targets, 49 for multisample load, 18 for gather4, 11 for blending, 5 for filtering, 2 for B5G6R5 counts other than 4×, and 1 for XR format support. Those are table-cell counts. Optional families and runtime applicability are prerequisites, particularly video, XR and 16-bpp extended formats. Examples of FL10_1 newly mandatory common blending are RGBA16 UNORM/SNORM, RGBA8 SNORM, RG16 UNORM/SNORM, RG8 SNORM, R16 UNORM/SNORM and R8 SNORM. Newly required filtering in the published table applies to R32F, RG32F, RGBA32F and the depth-view encodings R32_FLOAT_X8X24_TYPELESS and R24_UNORM_X8_TYPELESS. Single-channel `gather4` includes R32_FLOAT_X8X24_TYPELESS, R32_FLOAT, R24_UNORM_X8_TYPELESS, R16_FLOAT/UNORM/SNORM and R8_UNORM/SNORM. Verify actual FXC/driver opcode and permitted view type before projecting `textureGather` support. Non-red and comparison gather require additional operations or fail-closed validation.
- **MSAA source conflict.** The functional specification §19.2.5 and the FL10_1 per-format table agree that the generic required standard 4× floor is below 64 bits per sample. The API remarks for CheckMultisampleQualityLevels give a broader claim which excludes R32G32B32A32 and R32G32B32 only. Retain the discrepancy in the evidence log, use individual format rows and test 64-bit candidate formats such as RGBA16F. Multisample load or resolve being supported does not independently guarantee that a particular supported count exists. Depth/stencil view and compatible shader resource view format rows differ.
- **XR/packed source conflict.** The FL10_1 format table marks XR_BIAS general support required, whereas the D3D11 feature-level overview and exceptions page explicitly classify XR_BIAS as optional at both 10.x tiers. Treat as queried optional and keep the discrepancy visible. The FL10_1 table also marks B5G6R5 support and several MSAA uses required. Retain those cells and the runtime/driver applicability caveat from the D3D11 overview's 16-bpp row until scope is reconciled. Record conflicting source interpretations before setting a mandatory failure threshold.
- **Query method by facet.** Log HRESULT and value from `CheckFormatSupport`, relevant `CheckFeatureSupport` structures including FORMAT_SUPPORT2 where applicable, and `CheckMultisampleQualityLevels`. Use real operations where a capability has no query bit or has restrictions not encoded by the bit. A missing bit, a zero quality count, and a failed API call are distinct evidence fields.

## Shader and integration checkpoints

1. Split selected native level, backend implementation level and advertised contract. `adapter.rs:19–51` projects FL9_1 and labels higher native levels as such. The `instance.rs:86` switch selects FL9_1 for strict tests. Add deliberate selection for the new tiers and keep default and lower-tier fallback behavior verified. Each run records one requested level, native return value, `GetFeatureLevel`, public features/limits/flags, vendor/device/LUID, WDDM, runtime build, FXC version, and physical GPU identity.
2. Add a selected-level shader capability table and enforce it in Core and HAL. `shader.rs:18–37` has `ps_4_1` in the diagnostic compiler seam only (uses at lines 2379, 2536 and 2573). The Naga HLSL writer has shader model variants starting at 5.0 (`naga/src/back/hlsl/mod.rs:257`), and translation uses V5_0 options even for FL9 profiles (`shader.rs:566–615`). Pass explicit 4.0/4.1 constraints into codegen. Confirm register layout, sampler path, built-ins, comparison syntax, texture operations and instruction groups against real FXC targets. Preserve FL9 emulation and safety checks on their own code paths. Shader bytecode must be created and run on the target level in addition to passing the compiler.
3. Implement resources, views, uploads and resolves before raising a format or texture limit. Build descriptions and tests for 1D/2D/3D, arrays, typeless resource/view compatibility, BC4/5, depth/stencil and optional sampled MSAA. FL10_1 32-slot pipeline work crosses wgpu-hal and Core and owns all array-size assumptions. FL10_0 requires eight outputs with a shared blend equation, FL10_1 adds independent equations. Design equivalent validation at shader creation, pipeline creation, bind and draw, including the fail-closed boundaries.
4. Add queries and device lifecycle at the corresponding tier. GPU timers need a disjoint-aware interval around measured dispatch/draw work and separate reporting of CPU submit/readback. Horizon texture arrays and MRT need conversion and feature/limits checks in renderer paths. Compute culling requires optional 10.x constraints. Keep the CPU/direct-draw fallback at 10_x where indirect argument draws are unavailable. HDR additionally needs a compatible surface and operating-system display path. Quantify performance on paired same-device runs at matching settings with GPU timing where valid.
5. Run exact-level native and public test cases and retain separate outcomes for each matrix cell on all required targets. A higher-capability GPU forced to 10_x proves the application's downlevel path on that driver. It does not reproduce every historical 10_x implementation. For unknown native floating-point changes, test controlled FP16 blend and FP32 arithmetic/readback vectors rather than inferring from successful compilation. Native-only rows and source ambiguities remain open in the certification matrix even after the accessible public subset passes.
